# Civic Lens 設計原則（北極星）

> この文書は、Civic Lens のすべての設計判断の上位にある原則です。
> 機能追加・アーキテクチャ変更・ハッカソン対応など、どの作業でも最初にこの文書と照らし合わせてください。
> **この原則の変更には、プロジェクトオーナーの明示的な合意が必要です。** AI エージェントが独断で書き換えてはいけません。

---

## 1. 目的と手段

| | 内容 |
|---|---|
| **目的** | **真のシビックガバナンスの実現**。市民が行政を継続的に監視し、その記録が社会の共有財産として残り、行政の説明責任が実際に果たされる状態をつくる |
| **手段 1** | **情報公開のライフサイクルをオンチェーンの台帳にする**（開示請求 → 処分 → 審査請求 → 答申 → 裁決） |
| **手段 2** | **公共への貢献に報いる仕組み**（記録・検証・公開への貢献に対する報酬。法的確認を前提とする） |
| **手段 3** | **AI エージェント**（ニュースから論点を見つけて開示請求につなげる。記録と検証を代行して市民の負担を減らす） |
| **工程** | **ハッカソンは、実装への道筋に乗せるための工程**であり、それ自体は目的ではない |

背景の事実：日本には**国レベルの公的オンブズマン制度がありません**。自治体の公的オンブズマンも川崎市など一部にとどまります。その空白を、全国市民オンブズマン連絡会議をはじめとする市民団体の活動が支えてきました。Civic Lens は、その活動を**置き換えるのではなく、強くするための道具**です。

---

## 2. 最初のユーザーは市民オンブズマン

- **最初のユーザーであり、連携を目指す相手は、全国市民オンブズマン連絡会議をはじめとする市民オンブズマン団体**です。
  - 実務として開示請求と審査請求を最も多く行っている人たちであり、台帳の価値を最初に生み出せる人たちです。
  - 現時点では個人的なつながりがある段階で、**正式な提携はありません**。対外的な資料では、提携済みと受け取れる表現をしないでください。
- 機能は、**市民オンブズマンの実務フローに合わせて**設計します。
  - 例：複数機関への一括請求、法定期限の管理、審査請求への移行、結果の公表、調査結果の集計
- 最初の到達目標は、**実在の開示請求を約100件、台帳に記録すること**です。デモデータだけで完結する機能は、価値の証明になりません。

---

## 3. 設計原則

### 3.1 台帳が主役、お金は脇役
- 中核は「開示請求のライフサイクル台帳」です。支援金やエスクローは、台帳にぶら下がるオプションのモジュールにとどめます。
- 機能を判断するときは、次の3つを問います。
  1. **実在の開示請求の記録が増えるか**
  2. **記録の検証可能性が高まるか**
  3. **市民が行政を監視する力が強まるか**

  どれにも当てはまらない機能は優先度を下げます。

### 3.2 事実だけを、信頼度つきで記録する
- 台帳に載せるのは、日時・機関・処分の種類・文書のハッシュといった**客観的な事実**だけです。評価や批判は台帳に書きません。
- 記録にはそれぞれ**信頼度**を持たせます。
  - `自己申告`：請求者による記録
  - `AI検証`：通知書などを AI が読み取って照合したもの
  - `公的DB一致`：総務省の裁決DB・答申DBなどと突合できたもの
- 自治体の審査会の答申は総務省のDBに載らない場合があります。その場合は信頼度を下げたまま記録できるようにし、記録を止めてはいけません。

### 3.3 プライバシー：個人情報をオンチェーンに載せない
- 氏名・住所・連絡先、および開示された文書の本体はオンチェーンに記録しません。載せるのはハッシュとメタデータだけです。
- 文書の本体は、削除できるストレージに置きます。ブロックチェーンの記録は消せないため、誤って個人情報を載せると取り返しがつきません。

### 3.4 報酬は「成果」ではなく「貢献」に
- 審査請求の結論（認容など）に連動して第三者に金銭を渡す設計はしません。弁護士法72条（非弁行為）に触れるおそれがあるためです。
- 報酬の対象は、公共への貢献（記録・検証・開示文書の公開・データの整備）です。原資は寄附や助成金の資金プールにします（Quadratic Funding など）。
- 金銭的な報酬を導入する前に、弁護士への確認、または**グレーゾーン解消制度**での照会を行います。それまでは SBT（評判バッジ）など金銭以外の報酬を使います。
- 投機を目的としたトークンの発行を先行させません。

### 3.5 行政と敵対せず、透明性のインフラとして振る舞う
- 台帳は行政を攻撃する道具ではなく、**誰にとっても検証可能な公共の記録**です。将来的には自治体自身が記録する側に回れる設計にします。
- AI による「怒りの再現」はフィクションであることを常に明示します（既存の `PSEUDO_VOICE_DISCLAIMER`）。台帳の事実記録とは明確に分けます。
- AI は法的助言をしません。情報提供と書式作成の支援に徹し、請求や投稿を行うかどうかの最終判断は常にユーザーが行います。

### 3.6 Web3 を見せない
- 利用者にウォレット、手数料、署名を意識させません。手数料はアプリ側で負担し、組み込み型のウォレットを使います。ブロックチェーンは「改ざんされない保証」として裏側で働けば十分です。

### 3.7 オープンで、運営者に依存しない
- コードはオープンソースにし、台帳データはオープンデータ（出典を明記して再利用可能）にします。
- **Civic Lens の運営者がいなくなっても台帳が残り、市民団体が自分たちで使い続けられる**ことを目標にします。プラットフォームではなく、プロトコルとして作ります。

## 4. ハッカソンの位置づけ

同じ Civic Lens を2つの層に分け、それぞれの場で評価される層を見せます。どちらの場でも、上記の目的と原則は変えません。

| | Google Cloud Agentic AI Hackathon vol.5 | Colosseum Crypto World's Fair |
|---|---|---|
| 役割 | 国内での信用と AI エージェントの実力を示す | プロトコル化と、世界の資金・人材への入口 |
| 見せる層 | AI エージェント層（Gemini、自律的な動作） | 検証可能な台帳層（Solana、オープンなプロトコル） |
| 語り方 | 開示請求の挫折を AI が支える | 情報公開（FOIA）の流れを検証可能にする公共財。日本から始め、情報公開制度のある国へ広げる |
| 締切 | 2026-10-15 23:59 JST | 2026-10-12 23:59 PT（= 10-13 15:59 JST）、提出物は英語 |
| 制約 | 提出後 12/1 まで既定ブランチを変更できない | 既存コードの使用は可。ただし開示が必要 |

ハッカソンの成否よりも、**ハッカソンを通じて「最初の100件」を一緒に記録してくれる仲間と資金を得られるか**を重視します。

## 5. ぶれの兆候（アンチパターン）

次のような提案や実装が出てきたら、この文書に立ち返ってください。

- ハッカソンで受けることだけが理由の機能
- 審査請求の結論に連動して第三者に金銭を渡す仕組み
- 氏名・住所・文書本体をオンチェーンに載せる設計
- 行政や個人を断定的に批判する内容を、事実の記録と混ぜて保存すること
- 実際の利用者（市民オンブズマン）の実務を確かめずに作る機能
- 記録を増やすことより、トークンや投機的な仕組みを先に作ること
- 市民団体との提携を、事実より大きく見せる表現

## 6. マイルストーン

1. **2026年10月**：2つのハッカソンに提出する（AI 層と台帳層）
2. **2026年12月**：Google ハッカソン本選のピッチ（12/1）、Colosseum の結果発表（12/5 頃）
3. **2027年春まで**：市民オンブズマン団体と共に、実在の開示請求を約100件、台帳に記録する
4. **その後**：機関別の「通信簿」（処理日数・不開示率・答申で覆った割合）を公開し、自治体の参加を促す。報酬の仕組みを法的確認のうえで導入する
